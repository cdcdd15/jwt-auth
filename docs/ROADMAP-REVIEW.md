# Roadmap review against the learning objective

Reviewed 2026-10-31; current checkpoint P2.S1. Resolved items and remaining step-owned clarifications are separated below. The overall sequence is appropriate: learn MVC first, add password authentication, introduce JWT validation before login issuance, exercise negative paths, then compare and audit. Keep the existing P1–P5 sequence and compact endpoint set. The following recommendations clarify evidence and contracts; applicable handoffs are now incorporated in phase documents; they do not mark future work complete or authorize implementation.

## Recommended clarifications before the affected steps

| Priority / step | Recommendation | Learning benefit / acceptance evidence |
|---|---|---|
| Resolved — P1.S3 | Define whether a trace covers one servlet dispatch or the entire HTTP exchange. Record REQUEST versus ERROR dispatch explicitly when investigating errors. Keep the deliberately failing handler test-only if possible. | Avoid confusing MVC exception resolution, container error dispatch, and filter cleanup. Show actual callback order for unmapped and thrown-error cases, including absent hooks. Do not assume every 404 bypasses handler mapping. |

If unavailable, retain the explicit blocker rather than claiming verification. |

Spring's [CSRF guidance](https://docs.spring.io/spring-security/reference/6.5/servlet/exploits/csrf.html) supports the browser/Basic qualification. Its [Resource Server documentation](https://docs.spring.io/spring-security/reference/6.5/servlet/oauth2/resource-server/jwt.html) separates decoding/validation, conversion, and security-context establishment. These references describe the 6.5 line; use the project's exact resolved source/API versions for final call-level teaching evidence. Our required-claim and mode-contract recommendations are project design choices, not claims about automatically enabled defaults.

## Keep the course focused

Do not add databases, OAuth2 grants, frontend work, production deployment, or another security mechanism to solve documentation gaps. A short hypothesis, real HTTP experiment, measured trace, and explanation of the observed framework behavior are more valuable here than extra application layers. No new phase is recommended. The review itself changed documentation only. P1.S3 is now separately implemented: production traces remain REQUEST-only, and its test-only probe records REQUEST/ERROR callbacks under the same ID. See [P1.S3 evidence](learning/P1.S3-WALKTHROUGH.md). P2.S1 now resolves mode selection with one validated property, explicit conditional servlet registration, and a status-only 401 entry point. The outer trace filter was moved before the security proxy, with actual denial traces and proxy-call verification. The next implementation step is P2.S2. Remaining authenticated-context and detailed security diagnostics recommendations still apply to later steps.
