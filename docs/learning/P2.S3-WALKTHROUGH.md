# P2.S3 — Role authorization, denial paths, and context lifetime

## Objectives, prerequisites, and scope

Read [P2.S1](P2.S1-WALKTHROUGH.md) for true none-mode isolation and [P2.S2](P2.S2-WALKTHROUGH.md) for BCrypt, in-memory identities, and Basic authentication. This step finishes P2 by applying ADMIN authorization, distinguishing authentication challenges from access denial, observing selected security boundaries, and testing context cleanup and independent requests.

No JWT, OAuth2 grant, database, new production endpoint, or custom authentication algorithm is introduced. The new `SecurityTraceFilter` is observation-only. It neither reads credentials nor authenticates requests. `none` still has no security chain/proxy or identity infrastructure; its P1 traces are unchanged. Basic keeps public permitAll, authenticated user access, stateless policy, and the existing permitted ERROR dispatches.

The new policy is `/api/admin` → `hasRole("ADMIN")`, which checks `ROLE_ADMIN`. USER has `ROLE_USER`; ADMIN has `ROLE_ADMIN`. No hierarchy grants ADMIN a USER role: `/api/user` simply requires authentication, so both identities can use it. Roles describe authorities; authentication success alone does not imply every endpoint is permitted.

## Bean lifecycle and application-code commentary

All security configuration remains conditional on `app.security-mode=basic`. Spring creates the sink, users, encoder, DAO provider, and entry point, then builds the security chain. The new observer is directly constructed during chain construction, not independently component-scanned or servlet-registered. It exists only inside that chain and receives the same bounded `TraceEventSink` as the outer request filter/controller.

## Exact flow: authentication, authorization, and response

Tomcat accepts HTTP, enters the servlet filter chain, and the outer trace filter creates an ID. The registered DelegatingFilterProxy invokes FilterChainProxy, which selects the configured chain. BasicAuthenticationFilter parses supplied Basic credentials, invokes AuthenticationManager/ProviderManager, and uses DaoAuthenticationProvider → InMemoryUserDetailsManager + PasswordEncoder to check them, as in S2. Success establishes a SecurityContext; anonymous handling applies when credentials are absent.

The new observer records the resulting identity category before delegating. AuthorizationFilter evaluates the matching rule. Successful access continues to DispatcherServlet, handler mapping/adapter, controller, and Jackson conversion. MVC completion unwinds through the observer, which records exit. Security context-holder/proxy cleanup runs upstream before the outer trace filter completes.

An anonymous protected request reaches authorization, fails, and ExceptionTranslationFilter starts authentication through the entry point. A successfully authenticated USER denied admin access takes the access-denied-handler branch instead. Thus both requests fail authorization, but only the anonymous caller gets a 401 challenge; the authenticated USER gets 403 without a new challenge. See [ExceptionTranslationFilter's 6.5.6 API](https://docs.spring.io/spring-security/site/docs/6.5.6/api/org/springframework/security/web/access/ExceptionTranslationFilter.html) for this branching responsibility. The event wrappers record those actual branches; they do not replace them.

Invalid Basic credentials are different again: BasicAuthenticationFilter rejects before the observation filter/authorization/MVC path. The challenge event occurs, but neither identity-category nor authorization-exit events occur. Public permitAll does not ignore attempted invalid authentication.

The handlers use sendError. Tomcat subsequently dispatches to Boot's error handling with dispatcher type ERROR; the ERROR authorization rule allows the error JSON to preserve 401, 403, or 404. Production observation filters skip that redispatch. An initial REQUEST to `/error` is still protected and returns 401 without credentials. The [request authorization guide](https://docs.spring.io/spring-security/reference/6.5/servlet/authorization/authorize-http-requests.html) explains why dispatch authorization must be considered separately from initial URL authorization.

This diagram groups framework-owned calls; it is not a claim that every grouped method has an application event. Response bytes can be written before outer completion. Async dispatch remains outside the tested lifecycle. No JWT encoding/validation or signing keys exist in P2.

## What the traces prove

| Initial REQUEST | Exact event pattern after outer entry | Meaning |
|---|---|---|
| Anonymous public 200 | anonymous → MVC pre → public controller → MVC post/completion → authorization exit → outer exit | Public authorization allowed with security still active |
| Valid identity allowed 200 | authenticated → MVC pre → selected controller → MVC post/completion → authorization exit → outer exit | Authentication and authorization succeeded |
| Missing credentials 401 | anonymous → challenge → authorization exit → outer exit | Anonymous authorization failure translated into start authentication |
| Invalid Basic 401 | challenge → outer exit | Authentication failed before the downstream observer |
| USER admin 403 | authenticated → denied → authorization exit → outer exit | Authenticated caller lacks the required authority; controller not invoked |
| Authenticated missing route 404 | authenticated → MVC pre/completion → authorization exit → outer exit | Access allowed, resource lookup failed; no normal MVC postHandle |

`contextCleared=true` is separate **test-only evidence**, not a production sink event. The proxy spy calls the real method first, then checks the worker-thread holder in finally, before performing defensive test cleanup. A false observation would fail; the later defensive clear cannot make it true. We test initial REQUEST cleanup, not every internal ERROR/async dispatch cleanup.

## Comparative notes, questions, and exercises

Compared with S2, authentication, credential hashing, anonymous public access, controller JSON, mode selection, and servlet proxy registration remain the same. Admin now has a role rule. Observed security events extend Basic REQUEST traces; none's six-event success trace remains unchanged. ERROR permission was already present in S2 and is now exercised for preserved error results and protected direct `/error` access.

Framework SecurityContextHolderFilter/FilterChainProxy cleanup is different from a stateless session policy: we now observe no authentication in the worker holder after the proxy returns, in addition to checking independent request outcomes. Tests do not require a specific worker to handle consecutive requests, and they do not inspect another thread's ThreadLocal. Test cleanup happens after observation, so it cannot conceal a recorded leaked identity. No production filter clears context manually to manufacture this result.

Review questions:

1. Why does missing authentication get 401 while USER/admin gets 403? Exception translation distinguishes an anonymous caller needing authentication from an authenticated caller lacking authority.
2. Why does malformed Basic have no identity-category event? The Basic filter fails before the downstream observer, unlike anonymous authorization denial.
3. Why is security.authorization.exit present for both 200 and 403? It is a finally event for leaving the observation boundary, not an authorization-success marker.
4. Why is an anonymous token's authenticated flag insufficient? AnonymousAuthenticationToken can be marked authenticated while still representing an unauthenticated caller for access decisions.
5. Why is permitting ERROR different from permitting `/error`? Dispatcher type describes an internal error rendering pass; the URL can also receive an ordinary initial REQUEST, which remains protected.

Safe local exercises (revert afterward):

- Temporarily change admin authorization from hasRole("ADMIN") to authenticated(). Expect USER/admin to become 200 and the 403/denied-event test to fail, while password authentication still succeeds. Restore the role matcher.
- Temporarily remove the ERROR-dispatch permit rule and run the suite. Observe which original 401/403/404 body/status assertions change when error rendering itself requires authentication. Explain the second authorization decision, then restore the rule.
