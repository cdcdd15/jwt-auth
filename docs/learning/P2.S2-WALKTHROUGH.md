# P2.S2 — In-memory identities and HTTP Basic authentication

## Learning objectives and prerequisites

Read [P2.S1](P2.S1-WALKTHROUGH.md) for mode validation, servlet registration, chain selection, and authorization. This step supplies actual password authentication to its basic-mode chain: BCrypt, an in-memory user service, an explicit DAO authentication provider, and a shared Basic challenge entry point. Understand the distinction between incoming credentials, stored password hashes, authenticated identity, granted authorities, and endpoint authorization.

Only P2.S2 is implemented. No new production endpoint, role hierarchy, JWT dependency, database, session login, or custom authentication filter exists. Both `/api/user` and `/api/admin` still require only authentication. ADMIN-only enforcement, 403 tests, concurrent authenticated-context isolation, and detailed security event instrumentation remain P2.S3. USER and ADMIN identities already have distinct authorities, but merely creating authorities does not enforce a role policy.

The development accounts are the ones specified by the phase plan. Their literal demonstration passwords live in configuration source and tests, not a production-secret facility; they are never logged. They must not be used outside this local course. The encoder hashes them during bean creation, and each startup produces fresh salted hashes. `none` still has no user-service or encoder bean, security chain, or security servlet proxy.

## Bean construction and source commentary

The existing conditional `BasicSecurityConfig` owns every new bean, so all remain restricted to `app.security-mode=basic`. Boot's generated-user auto-configuration remains excluded. Spring resolves bean-method parameters by type and constructs collaborators before the chain that needs them. No application service or controller needs to inject a password or user identity.

## Request lifecycle and failure branches

The successful path remains HTTP client → embedded Tomcat → servlet filters → outer RequestTraceFilter → DelegatingFilterProxy → FilterChainProxy → selected security filters. The new `BasicAuthenticationFilter` converts the Basic header to an unauthenticated `UsernamePasswordAuthenticationToken` and submits it to an AuthenticationManager. `ProviderManager` dispatches to a supporting provider. The DAO provider loads UserDetails from `InMemoryUserDetailsManager` and checks the supplied password using the encoder.

Successful authentication produces an authenticated token with principal and authorities. ProviderManager's normal credential erasure removes credentials from that token; the Basic filter establishes a request SecurityContext. Authorization allows the authenticated request. DispatcherServlet selects the handler, RequestMappingHandlerAdapter invokes the controller, and Jackson serializes the same map as before. MVC/security callbacks unwind and the outer filter publishes its completed trace. The test probe observes the authenticated identity during MVC, not from the test thread's own SecurityContext.

These responsibilities are documented in Spring's [DAO provider description](https://docs.spring.io/spring-security/reference/6.5/servlet/authentication/passwords/dao-authentication-provider.html). Our observed principal/authority/erasure checks are listed below; the password-check method call itself is not an application trace event.

Missing credentials and bad credentials take different paths. Without a Basic header, the Basic filter continues; anonymous access to a protected route is rejected by authorization and translated into the entry point. With malformed or invalid Basic credentials, the Basic filter handles authentication failure before application dispatch. A wrong password and unknown username return the same status/challenge; they do not expose account existence. Invalid supplied credentials also fail on `/api/public`: permitAll affects authorization, not an earlier failed authentication attempt. Public access without credentials remains 200.

The shared framework entry point calls `sendError`, which triggers Boot's ERROR dispatch and JSON error handling for these JSON-accepting clients. The newly permitted ERROR dispatch renders 401 rather than replacing it with another authorization failure. The production trace and principal probe intentionally record only the initial REQUEST. Therefore a two-event denial trace means no original application handler ran; it does **not** claim that DispatcherServlet/BasicErrorController never ran during error rendering. This differs from S1's empty status-only response. Basic mechanics are described in the [framework Basic guide](https://docs.spring.io/spring-security/reference/6.5/servlet/authentication/passwords/basic.html); the resolved 6.5.6 entry-point bytecode was also inspected to confirm `sendError`.

        alt public endpoint
            Z->>M: permitAll
            M-->>T: 200 JSON

HTTP Basic uses Base64 encoding, not encryption. Local HTTP is only the test/demo transport; real use requires transport protection. Password hashing at rest does not encrypt the request header. No Authorization headers, password hashes, or authentication objects are printed by the tracing code. JWT claims/signing and Nimbus are not introduced in this step.

## Review questions and safe exercises

1. Why can invalid credentials fail on a public route? Authentication processing precedes the authorization rule; permitAll does not suppress an attempted Basic authentication failure.
2. Why does hashing the password again not give a reliable equality check? BCrypt generates a fresh salt; `matches` uses the parameters stored in the existing hash.
3. Who puts the authenticated token into SecurityContext? The Basic authentication filter does so after manager/provider success; the user service merely supplies user details.
4. Why does the probe read context inside MVC? SecurityContextHolder is normally thread-bound; a test-thread read would not describe the Tomcat request thread.
5. Why permit ERROR dispatches? The standard entry point invokes sendError, and Boot must render that error without replacing it with a second protected-request failure. Initial `/error` requests still require authentication.
6. Does ROLE_ADMIN already enforce admin-only access? No. P2.S3 adds that endpoint rule; S2 only establishes authentication and authorities.

Safe temporary modifications, reverted afterward:

- Change one user's role to a different role and run verification. Valid login can still succeed, but the expected-authority assertion fails. Restore it. This separates identity authentication from role mapping and endpoint policy.
- Change only the realm string, then run verification. Authentication success tests can still pass, while challenge-header assertions fail. Restore the realm to recover the documented wire contract.

The shared plain MVC controllers, bounded tracing, mode validation, and none isolation remain unchanged. S1's no-Basic-filter/no-challenge assertions are superseded; its recorded output is historical. Context-isolation under concurrent authenticated identities, detailed provider/security traces, ADMIN restrictions, and 403 paths are not claimed here. Next step: P2.S3 only on a separate request.
