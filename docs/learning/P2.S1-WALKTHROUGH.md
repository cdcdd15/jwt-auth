# P2.S1 — Security-chain registration and real plain-mode isolation

## Objectives, prerequisites, and step boundary

Read the P1 walkthroughs first: Tomcat, MVC handler discovery, controller invocation, JSON conversion, and error dispatch remain the foundation. This step adds Spring Security to the classpath while preserving a genuinely unfiltered plain mode. Learn the distinction between a servlet registration, a `FilterChainProxy`, a `SecurityFilterChain`, and an authorization rule.

The new property is `app.security-mode`. Missing means `none`; explicit `none` and `basic` are supported. Values are validated exactly; blank, unknown, combined, and future `jwt` values fail configuration creation. Spring's normal property-source precedence chooses one effective value; this is not a set of combinable profiles. No JWT mode is implemented.

The name `basic` identifies the future completed mode, but S1 only creates its security infrastructure. **No Basic credential filter, users, password encoder, login form, or Basic challenge exists yet.** An explicit status-only 401 entry point makes S1 independently verifiable without implementing S2. Admin currently requires authentication, not ADMIN; role authorization belongs to S3.

## Configuration and bean creation

The starter adds Spring Security 6.x libraries to both runtime modes. The application excludes Boot's default security chain, servlet-proxy auto-registration, and generated-user configuration. A component-scanned configuration validates the mode. A separate conditional configuration uses `@EnableWebSecurity` only in `basic`, creates the chain, and explicitly registers a servlet proxy.

| Mode | Security libraries | Chain / FilterChainProxy bean | Security servlet proxy | Result |
|---|---|---|---|---|
| `none` or missing property | Present | Absent | Absent | Ordinary P1 request path; Authorization headers ignored |
| `basic` at S1 | Present | Present | Present | Public allowed; other requests require authentication, returning 401 while no authentication mechanism is installed |
| Other / `jwt` | Present | Not a supported configuration | Application startup fails | No silent fallback to unprotected operation |

A `permitAll` chain would still run security infrastructure. Here `none` does not build such a chain at all. P1's historical dependency-absence proof is no longer applicable; bean and actual servlet-registration absence are the current proof. No custom authentication filter is introduced.

## Requests through the framework

The framework's [servlet architecture](https://docs.spring.io/spring-security/reference/6.5/servlet/architecture.html) distinguishes the container proxy, security proxy, and selected chain. Our actual configured filter list appears below; membership/order is not proof that every filter authenticates on each request.

In basic public access, Tomcat enters servlet filters and the outer trace filter records entry. `DelegatingFilterProxy` invokes `FilterChainProxy`; its configured chain processes the request. The context-holder filter manages request context access, the anonymous filter supplies anonymous authentication when needed, and the authorization filter permits public access. The remaining servlet chain reaches DispatcherServlet, handler mapping, handler adapter, controller, and Jackson conversion. MVC completion and security cleanup unwind before the outer filter publishes its snapshot.

For a protected request, authorization rejects the anonymous caller. Exception translation invokes our authentication entry point, which sets 401. MVC never runs. The outer trace contains only filter entry/exit. A public route's `permitAll` does not remove security filters; a Mockito spy observes actual proxy calls on the real HTTP path. None uses the ordinary Tomcat/filter/MVC path without entering a security proxy at all.

```mermaid
sequenceDiagram
    participant C as HTTP client
    participant T as Tomcat / RequestTraceFilter
    participant P as DelegatingFilterProxy → FilterChainProxy
    participant S as Selected security filters
    participant M as DispatcherServlet / MVC / controller
    C->>T: GET /api/public or protected path
    T->>T: filter.entry; generated correlation ID
    alt none mode
        T->>M: servlet chain (no security registration)
        M-->>T: normal JSON response
    else basic mode
        T->>P: servlet filter delegation
        P->>S: selected SecurityFilterChain
        alt public authorization allowed
            S->>M: continue servlet chain
            M-->>S: JSON 200
        else protected anonymous request
            S->>S: authorization denied
            S->>S: exception translation → entry point sets 401
            Note over M: MVC is not invoked
        end
        S-->>P: unwind; framework context cleanup
        P-->>T: return
    end
    T->>T: filter.exit; publish snapshot
    T-->>C: HTTP response
```

None's 404/500 ERROR-dispatch behavior remains verified by the P1 suite. Security registration also includes ERROR in basic, but secured error-dispatch policies are not exercised here. Async lifecycle instrumentation remains outside scope. We do not infer context-isolation under real authenticated identities yet; that requires S2 users and later diagnostics.

Authentication establishes identity, whereas authorization decides access. S1 has anonymous-context infrastructure and authorization but no successful credential authentication. `AuthenticationManager` plumbing is framework infrastructure; no application provider, `UserDetailsService`, or `PasswordEncoder` is configured. Default access-denied handling remains framework-owned; an authenticated 403 scenario is not implemented/tested until roles and identities exist. JWT/Nimbus/RS256 remain future work.

The [CSRF documentation](https://docs.spring.io/spring-security/reference/6.5/servlet/exploits/csrf.html) explains why automatically supplied browser credentials can leave Basic vulnerable even without sessions. A real browser application needs its own CSRF design; this course does not add one.

## Review questions and safe exercises

1. Why can none have security jars without security processing? Libraries do not register themselves here; excluded auto-configuration and conditional explicit registration leave no security proxy/chain in that mode.
2. Why does public access not prove absence? `permitAll` is evaluated within an active chain; the public basic test verifies proxy invocation despite 200.
3. Why does a protected S1 response lack a Basic challenge? The current entry point only sets status; HTTP Basic is disabled until S2.
4. Why move the tracing filter outward? An inner filter would never see a security rejection that short-circuits the chain before it.
5. Why is statelessness not a general CSRF solution? Browsers may resend credentials automatically; API session policy and browser credential behavior are different concerns.

Temporary exercises, revert after observing:

- Run the application with `--app.security-mode=basic` and request public/user. Expect 200 and 401 respectively. Run with `--app.security-mode=jwt` and expect startup failure, not a silently unsecured server.
- Change the public rule to `authenticated()` and run verification. Expect the public basic test to fail with 401 while none-mode endpoint tests remain green. Restore the public rule afterward.

P1 walkthroughs now represent historical checkpoints: their claims that security is absent from the classpath apply to P1 artifacts, not this artifact. Their servlet callback logic remains valid in explicit none contexts, but the application annotation and outer filter registration changed here. No P2.S2 identity work, P2.S3 role policy, or JWT code is implemented. Next step: P2.S2 only when requested.
