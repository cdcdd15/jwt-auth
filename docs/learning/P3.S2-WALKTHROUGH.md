## Objectives, prerequisites, and boundary

Read [P3.S1](P3.S1-WALKTHROUGH.md) for RSA/JWS anatomy and the [claim contract](../JWT-CLAIM-CONTRACT.md) for application policy. This step connects signatures and claims to real HTTP bearer authentication using Spring Security Resource Server. Distinguish decoding, signature verification, claim validation, authority conversion, context establishment, and endpoint authorization.

Runtime `app.security-mode=jwt` is now supported. None/basic retain their existing behavior and isolated test contexts. JWT mode loads a local public key only, has no issuer/encoder bean, and exposes no `/auth/login`. Test code alone signs tokens with ephemeral private keys. P3.S3 adds local credential-to-token issuance; P4 completes authorization edge cases, the negative-token suite, and detailed JWT diagnostics. No OAuth2 grant, authorization server, redirect login, external IdP, database, or custom bearer authentication filter is added.

## Startup and key ownership

Replace S1's explicit test-scoped JOSE dependency with `spring-boot-starter-oauth2-resource-server`. Boot now manages runtime Resource Server and JOSE dependencies; the old test scope must not shadow the starter's runtime graph. Security libraries do not activate a chain in none: conditional configurations and explicit servlet registration still control activation.

JWT startup requires `app.jwt.public-key-path`, a filesystem path to an X.509 SubjectPublicKeyInfo RSA PEM (`BEGIN PUBLIC KEY`). This is not a private-key path, certificate parser, HTTP URL, or discovery endpoint. Missing/unreadable/invalid/undersized keys fail initialization; there is no fallback generation or remote key fetch. The accepted modulus is at least 2048 bits. Production time uses UTC system clock; tests select a fixed clock through a test-only primary bean.

Example when you already have a local development public key:

```bash
mvn spring-boot:run -Dspring-boot.run.arguments="--app.security-mode=jwt --app.jwt.public-key-path=/absolute/path/to/public.pem"
```

The matching private key stays with the test issuer in this step. No public-key fixture or private key is committed. HTTP tests create a temporary public-only PEM, load it through the real application configuration, and delete it afterward. The decoder retains the parsed public key in memory, so it does not reopen the file per request.

## Exact successful and failed request lifecycle

The client presents `Authorization: Bearer <token>` over HTTP to Tomcat. Servlet processing reaches the outer request tracer, DelegatingFilterProxy, and FilterChainProxy. The selected security chain's BearerTokenAuthenticationFilter extracts the bearer credential and submits a bearer authentication request through AuthenticationManager/ProviderManager to JwtAuthenticationProvider.

NimbusJwtDecoder verifies the JWS against the trusted public key and configured algorithm, constructs normalized claims, and runs the aggregate validators. Successful validation allows JwtAuthenticationConverter to create a JwtAuthenticationToken with ROLE authorities. The bearer filter establishes the authenticated SecurityContext. The observation filter records authenticated state, then authorization permits the matching endpoint. DispatcherServlet resolves the handler; its adapter invokes the controller; Jackson writes unchanged JSON. MVC and filter completion unwind into the bounded trace snapshot.

These responsibilities follow Spring's [Resource Server JWT architecture](https://docs.spring.io/spring-security/reference/6.5/servlet/oauth2/resource-server/jwt.html). Nimbus verification alone does not establish context or decide endpoint access. A matching signature can still fail issuer/audience/time validation. A validated identity can still lack authorization; the full insufficient-role HTTP matrix is assigned to P4.S1.

Wrong signature, expired token, wrong issuer, or wrong audience fails before the original application handler and the downstream observation filter; the standard entry point returns 401 with a Bearer challenge. Basic credentials are not processed as Basic authentication here: no bearer token is found, anonymous authorization fails, and a Bearer challenge is returned. Anonymous public access is allowed. These tests assert challenge scheme/status, not the entire framework-generated error-description string.

```mermaid
sequenceDiagram
    participant C as RestAssured client
    participant T as Tomcat / outer RequestTraceFilter
    participant B as BearerTokenAuthenticationFilter (inside FilterChainProxy)
    participant P as ProviderManager / JwtAuthenticationProvider
    participant D as NimbusJwtDecoder
    participant V as Contract / issuer / timestamp validators
    participant A as JwtAuthenticationConverter
    participant M as AuthorizationFilter / MVC / controller / Jackson
    C->>T: GET with bearer token signed by test issuer
    T->>B: registered servlet proxy → selected chain
    B->>P: authenticate bearer credential
    P->>D: decode
    D->>D: verify RS256 using local public key
    alt signature invalid
        D-->>B: authentication failure through provider
        B-->>T: 401 + Bearer challenge
    else signature valid
        D->>V: validate normalized claims
        alt issuer/audience/time/contract invalid
            V-->>B: failure through decoder/provider
            B-->>T: 401 + Bearer challenge
        else valid
            V-->>P: validated Jwt
            P->>A: convert trusted roles
            A-->>B: JwtAuthenticationToken
            B->>B: establish SecurityContext
            B->>M: continue; authorize endpoint
            M-->>T: 200 JSON for tested allowed identity
        end
    end
    T->>T: outer finally → publish trace
    T-->>C: final response and correlation ID
```

This is the logical bearer flow, not a recording of every framework call. SecurityTraceFilter events and controller reachability are observed; provider/decoder call sequence is explained from framework responsibilities. Context cleanup in Basic was directly observed in P2; JWT-specific authenticated-context diagnostics remain P4.S3. No async lifecycle claim is added.

## Review questions, comparisons, and exercises

Compared with Basic, Tomcat/MVC/controllers and endpoint access policy are unchanged. Basic checks username/password against BCrypt-backed users; JWT verifies a signed bearer credential with a public key and validates its claims, then creates authentication. No in-memory credential lookup occurs for these JWT requests. Both secured modes use Spring's built-in filters; none uses no security proxy at all. Base64URL claims remain readable, not encrypted; passwords/private keys must never be claims or trace values.

1. Why can a valid signature still result in 401? The token may have the wrong issuer/audience, an invalid time window, or violate required claim shape.
2. Who creates authenticated context? The Spring authentication/provider/converter/filter pipeline; Nimbus signature verification alone does not.
3. Why supply both a timestamp validator and an exp-presence check? Checking a present timestamp is distinct from requiring it to exist.
4. Why does Basic-only access get a Bearer challenge? This mode has no Basic authentication filter; it requests its configured bearer mechanism.
5. Why is issuer a URN instead of an IdP endpoint? This course trusts a local public key and compares issuer text without discovery or OAuth2 grants.
6. Why do fixed tests accept their 2030 tokens today? Decoder validation uses the injected fixed clock, not the machine's current year.

Safe temporary exercises (revert after observation):

- In the test token helper, temporarily replace the valid audience with `other-api` while leaving the decoder policy unchanged. Expect normally valid signed-token cases to return 401, proving signature trust is not sufficient for API targeting. Restore the fixture.
- Change the fixture's fixed decoder clock far past expiration while preserving token claims. Expect valid-token cases to fail with 401. Restore the clock; do not introduce a sleep-based test.

P3.S2 stops here. P3.S3 is next: local credential-to-token issuance. P4 remains responsible for the exhaustive role/error/time/algorithm matrix and detailed JWT diagnostics. No login endpoint or production signer is added in this step.
