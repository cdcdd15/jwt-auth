## Objects, registration, and lifecycle

Spring discovers `TraceConfiguration` through the existing application component scan. Its bean methods create one `TraceEventSink`, one `FilterRegistrationBean`, and one `WebMvcConfigurer`. The registration object owns a `RequestTraceFilter`; the MVC configurer creates and registers a `MvcTraceInterceptor`. Neither callback object is component-scanned independently, preventing accidental duplicate registration. Both receive the same sink explicitly through constructors. The controller's single constructor also receives that sink automatically; it needs no `@Autowired` annotation.

The filter and interceptor are shared across requests. Their only instance field is a final sink reference. Active event lists live on individual servlet requests, not shared fields or a `ThreadLocal`. Completed immutable snapshots live in the sink under generated UUIDs. The last 128 completions are retained; older snapshots are evicted. This is a bounded educational observer, not a durable audit log or tracing service. No HTTP endpoint exposes stored traces.

## Request sequence and response unwinding

Tomcat accepts HTTP and enters its servlet filter chain. At our filter, a UUID and active list are created. After `filter.entry`, `chain.doFilter` eventually reaches `DispatcherServlet.doDispatch`. `RequestMappingHandlerMapping` resolves the controller method and its interceptor chain. `HandlerExecutionChain.applyPreHandle` invokes `preHandle`; `RequestMappingHandlerAdapter` then invokes the controller through MVC's method-invocation machinery.

The controller records its event and returns a map. `RequestResponseBodyMethodProcessor` and Jackson serialize it during handler-adapter processing. Therefore `postHandle` is after response-body conversion for these REST methods, not a reliable place to change already-written headers or JSON. MVC calls `afterCompletion`, returns through the servlet chain, and our finally block records exit and publishes the snapshot. Tomcat completes HTTP handling. The client can receive response bytes before the filter's finally block finishes; tests wait for publication instead of assuming socket completion implies trace availability.

```mermaid
sequenceDiagram
    participant C as HTTP client
    participant T as Tomcat / servlet filters
    participant F as RequestTraceFilter
    participant D as DispatcherServlet
    participant I as MvcTraceInterceptor
    participant H as DemoController
    participant S as TraceEventSink
    C->>T: GET /api/public
    T->>F: doFilterInternal
    F->>S: begin; record filter.entry
    F->>D: chain.doFilter (through remaining chain)
    D->>D: handler mapping selects method
    D->>I: preHandle → true
    I->>S: interceptor.preHandle
    D->>H: handler adapter invokes publicEndpoint
    H->>S: controller.public
    H-->>D: map → response-body processor / Jackson
    D->>I: postHandle
    I->>S: interceptor.postHandle
    D->>I: afterCompletion
    I->>S: interceptor.afterCompletion
    D-->>F: servlet processing returns
    F->>S: filter.exit; complete immutable snapshot
    F-->>T: filter returns
    T-->>C: 200 JSON + X-Correlation-ID
```

The diagram's last arrow is conceptual response completion, not a guarantee that no bytes were sent earlier. The observed trace covers these application hooks, not the exact ordering of all Boot/Tomcat filters. Spring Security's `FilterChainProxy` is absent; a `permitAll` chain is not substituted.

## Exception and async boundaries

These are framework qualifications, not newly executed error-path tests. If a controller throws, normal `postHandle` is skipped; MVC can invoke exception resolvers and then completion callbacks. `afterCompletion` applies when the interceptor's `preHandle` completed successfully and returned true. An exception resolved within MVC may not appear as its exception argument. If dispatch reaches our filter and fails downstream, `finally` still publishes its partial event list.

```mermaid
sequenceDiagram
    participant F as RequestTraceFilter
    participant D as DispatcherServlet
    participant I as MvcTraceInterceptor
    participant H as Handler
    F->>D: chain.doFilter
    D->>I: preHandle
    alt synchronous success (tested)
        D->>H: invoke
        H-->>D: result and conversion
        D->>I: postHandle then afterCompletion
    else handler throws (not tested until S3)
        D->>H: invoke
        H-->>D: exception
        D->>D: exception resolvers / propagation
        D->>I: afterCompletion when applicable; no normal postHandle
    end
    D-->>F: return or throw
    F->>F: finally records exit and completes trace
```

A later ERROR dispatch is not included. Missing resources can involve a static-resource handler, not a demo controller. P1.S3 will establish actual error behavior. Async MVC can exit the initial dispatch before handler completion and redispatch later. This sink finalizes at initial filter exit and ignores redispatch callbacks; it is deliberately not an async lifecycle tracer. Supporting async would require redesigning completion ownership and thread safety, not merely changing a diagram.

## Review questions and exercises

1. Why does filter exit follow interceptor completion? The filter delegates to a nested servlet dispatch and resumes only when that dispatch returns or throws.
2. Why can a valid HTTP response arrive before the trace is available? Response output can be flushed before the surrounding filter completes.
3. Why does the interceptor return true? MVC must continue to the selected handler; false would short-circuit it.
4. Why avoid a global active list? Concurrent requests would mix events; the request object already provides isolated storage.
5. Does `postHandle` precede JSON serialization here? No: REST return-value conversion occurs inside handler-adapter execution.

Safe temporary exercises, reverting edits afterward:

- Remove `chain.doFilter`, run the suite, and observe missing JSON/controller/interceptor events and failing assertions. Restore delegation to recover the nested flow.
- Change one controller event name and run verification. HTTP contract tests still pass, but ordering tests fail with an exact-list mismatch, showing the difference between response behavior and lifecycle evidence.

Compared with S1, routing, Tomcat, JSON conversion, and anonymous access are unchanged; observation hooks and bounded trace retention are new. Basic/JWT remain planned. No AuthenticationManager, provider, password encoder, SecurityContext, entry point, or access-denied handler is implemented. The [combined guide](../FLOWS-COMPARED.md) explains future differences, including Resource Server validation without OAuth2 grant flows. No JWT/private-key processing occurs in S2.
